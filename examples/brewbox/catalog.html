01

System context

Business
Use when
You need to explain what the system is, who uses it, and what it depends on, to people who don't care about the technology.
In this example
BrewBox as one box running on AWS. Its users are customers and support agents, and it depends on Stripe, SAP, the 3PL warehouse and Amazon SES for email. This is the first diagram you show in a kickoff.

03

Business process

Business
Use when
You're agreeing with stakeholders on who does what, and on what happens when something fails.
In this example
Monthly subscription renewal, in swimlanes per party. It shows the rule that payment is retried every 24 h and the subscription pauses after the 3rd failure.

05

Sequence diagram

Tech
Use when
One scenario has many steps across systems (an API flow, an integration handshake, auth), and the order of the steps matters.
In this example
Checkout with 3-D Secure. The order becomes PAID only when the Stripe webhook arrives through API Gateway, and fulfilment then runs asynchronously via EventBridge, SQS and Lambda.
Mermaid source 
sequenceDiagram
  autonumber
  actor C as Customer
  participant W as Web shop<br/>(Next.js)
  participant G as API Gateway
  participant O as Order Service<br/>(Node.js, Fargate)
  participant S as Stripe
  participant E as EventBridge
  participant F as Fulfilment Worker<br/>(SQS → Lambda)
  participant H as 3PL Warehouse
  C->>W: Click "Pay"
  W->>G: POST /orders (JWT)
  G->>O: Forward request
  O->>O: Save order in Aurora (PAYMENT_PENDING)
  O->>S: Create PaymentIntent
  S-->>O: requires_action (3-D Secure)
  O-->>W: 202 + client secret
  W->>C: Show bank 3-D Secure screen
  C->>S: Confirm in bank app
  S-)G: Webhook payment_intent.succeeded
  G->>O: Forward webhook
  O->>O: Status = PAID
  O-)E: PutEvents OrderPaid
  E-)F: Rule → SQS → Lambda
  F->>H: Upload order file (SFTP)
  W-->>C: "Thanks, your box is on its way"
06

State diagram

Tech
Use when
An entity has a lifecycle with rules about which transitions are allowed.
In this example
The life of an order. Use it to settle questions like "can we refund an order that hasn't shipped yet?" (yes: Paid → Refunded). The note shows how each transition becomes an EventBridge event.
Mermaid source 
stateDiagram-v2
  direction TB
  [*] --> Created
  Created --> PaymentPending: checkout
  PaymentPending --> Paid: Stripe webhook succeeded
  PaymentPending --> PaymentFailed: card declined
  PaymentFailed --> PaymentPending: retry (max 3)
  PaymentFailed --> Cancelled: 3rd failure
  Paid --> Picking: sent to warehouse
  Picking --> Shipped: tracking number received
  Shipped --> Delivered: carrier confirms
  Paid --> Refunded: support refund
  Delivered --> Refunded: complaint accepted
  Delivered --> [*]
  Cancelled --> [*]
  Refunded --> [*]
  note right of Paid
    Every transition is saved in Aurora
    and published to EventBridge
    (OrderPaid, OrderShipped, ...)
  end note
07

ER diagram

Tech
Use when
You're designing or explaining a data model, or mapping fields between two systems.
In this example
Tables in Aurora PostgreSQL. One order can have several payment attempts but at most one shipment, and each customer is linked to their Cognito user.

08

Deployment

Tech
Use when
Ops, security or compliance review: where does each part run, in which region and network, and how does it reach other environments?
In this example
Production in eu-central-1 across 3 AZs: edge services, a VPC for Fargate, Lambda and Aurora, regional managed services, and a Site-to-Site VPN to the on-prem SAP. Logical level, no AWS icons.
